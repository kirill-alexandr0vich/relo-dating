# Relo Dating

Мобильное приложение знакомств для релокантов. React Native + TypeScript, Firebase (Auth/Firestore/Storage/Functions/Messaging), видеозвонки через Agora SDK.

Полное техническое задание: [`docs/TZ.md`](docs/TZ.md). Сверка реализации с ТЗ по каждому разделу, включая известные отклонения и пробелы: [`docs/STATUS.md`](docs/STATUS.md).

## Архитектура (Feature-Sliced Design)

```
src/
  app/        — точка входа, навигаторы (Root/AuthFlow/Tab), провайдеры (auth, safe area, firebase init, i18n)
  pages/      — экраны (композиция виджетов/фич под конкретный роут)
  widgets/    — крупные самостоятельные блоки UI, не завязанные на конкретные страницы
  features/   — юзер-кейсы с бизнес-логикой (sign-in, complete-registration, swipe-card, ...)
  entities/   — бизнес-сущности (user, match, chat, event) — модели, API, база UI
  shared/     — переиспользуемое без бизнес-смысла: UI-кит, i18n, константы, обработка ошибок Firebase
```

Импорты — только вниз по слоям, наружу слайс отдаёт только через свой `index.ts`. Алиасы путей (`app/*`, `pages/*`, `widgets/*`, `features/*`, `entities/*`, `shared/*`) настроены в `tsconfig.json` и `babel.config.js`.

Навигаторы (`app/navigation/RootNavigator.tsx`, `AuthFlowNavigator.tsx`, `TabNavigator.tsx`) сознательно лежат в `app/`, а не в `widgets/`: они напрямую ссылаются на конкретные `pages/*`, а `widgets` не может импортировать `pages` (это слой выше).

### Firebase

Перед первым запуском на устройстве/эмуляторе положите нативные конфиги проекта Firebase:

- Android: `android/app/google-services.json`
- iOS: `ios/GoogleService-Info.plist`

`@react-native-firebase/app` инициализируется автоматически на основе этих файлов, дополнительная JS-конфигурация не требуется.

### Авторизация (раздел 3 ТЗ)

Реализованы 4 способа входа (Apple, Google, Email/пароль, телефон по SMS-коду) с объединением аккаунтов и обязательными полями регистрации (имя, страна, родной язык). Прежде чем это заработает на устройстве, нужно донастроить нативную часть — этого нельзя сделать без реального проекта Firebase:

- **Google Sign-In**: вписать `webClientId` (из Firebase Console → Project settings → аккаунты Google) в `src/shared/config/googleSignIn.ts`. Для Android также нужен SHA-1/SHA-256 отпечаток в настройках проекта Firebase.
- **Sign in with Apple**: включить capability "Sign In with Apple" в Xcode (`ios/ReloDating/ReloDating.entitlements`) и в Apple Developer Console; в Firebase Console включить провайдер Apple.
- **Phone Auth**: включить провайдер "Phone" в Firebase Console. Для iOS нужен APNs-ключ (silent push для проверки reCAPTCHA), для Android — включённый Play Integrity API.
- После добавления нативных зависимостей (`@react-native-google-signin/google-signin`, `@invertase/react-native-apple-authentication`) выполнить `cd ios && bundle exec pod install`.

Экран выбора способа входа блокирует все 4 кнопки чекбоксом "мне есть 18 лет" (п.9 ТЗ) — в фиксированном списке экранов онбординга (3.3) для этого чекбокса нет отдельного шага, поэтому он размещён на первом экране флоу, до создания любого аккаунта.

### Профиль и модерация (разделы 3.2, 7.2 ТЗ)

Экран "Профиль" — редактирование опциональных полей (фото, юзернейм, "о себе", возраст, пол, кого ищет, "здесь с", увлечения) и кнопка выхода из аккаунта.

`name`/`bio`/`avatarUrls` **нельзя** писать напрямую с клиента (см. `firestore.rules`) — они проходят через модерацию (7.2) и пишутся только Cloud Functions:

- `submitProfileText` — проверяет имя/"о себе" на профанити (`obscenity`, только английский словарь; для русского нужен свой список слов или внешний API) и сохраняет.
- `submitProfilePhoto` — клиент грузит фото во временную папку `users/{uid}/pending/...` (Storage), функция прогоняет её через Google Cloud Vision SafeSearch и либо переносит в публичную `users/{uid}/photos/...`, либо удаляет и отклоняет.
- `removeProfilePhoto` / `reorderProfilePhotos` — удаление и смена порядка (первое фото = главное).

Юзернейм — отдельная механика: коллекция `/usernames/{lowercase}` резервирует имя транзакцией на клиенте (без Cloud Function, модерация не нужна — юзернеймов нет в списке полей 7.2).

**Чтобы это заработало на реальном проекте:**
- В Google Cloud Console включить **Cloud Vision API** для проекта Firebase (Cloud Functions использует Application Default Credentials — отдельный API-ключ не нужен).
- Задеплоить функции и правила: `firebase deploy --only functions,firestore:rules,firestore:indexes,storage:rules` (из корня репозитория; `functions/` — отдельный npm-пакет, `cd functions && npm install` перед первым деплоем).
- `react-native-image-picker` — новая нативная зависимость, после установки выполнить `cd ios && bundle exec pod install`.

### Друзья и сообщения (разделы 5, 6 ТЗ)

Мэтч и дружба — раздельные сущности, обе дают доступ к чату. `/friends`, `/chats` и `/chats/{id}/messages` используют тот же детерминированный id пары (`sorted(uidA, uidB).join('_')`), что и `/matches`, — вынесено в `functions/src/shared/pairId.ts`.

- Заявки в друзья (по `@username` через `/usernames/{lowercase}` или по QR-диплинку `relocantapp://addfriend/{uid}`) и их принятие/отклонение — прямые клиентские записи в `/friends`, разрешённые правилами Firestore (`get()`/`exists()` проверяют, что мэтч действительно есть для `addedVia:'match'`, и что документ ещё не существует). Отдельный Cloud Function не нужен — модерация на дружбу не распространяется (её нет в списке полей 7.2).
- **Сообщения** — только через Cloud Function `sendMessage`: проверяет профанити (тот же `obscenity`, что и в профиле) и разрешён ли контакт (мэтч — всегда; принятая дружба — только если у обеих сторон включено "Разрешить сообщения от друзей без мэтча"; блокировка — никогда). Прямая запись клиента в `/chats/*/messages` запрещена правилами.
- **Блокировка** — Cloud Function `blockUser`: удаляет общие `/matches` и `/friends` (они Cloud-Function-only) и добавляет в `blockedUserIds`. Разблокировка — обычная запись клиента (`arrayRemove`), других побочных эффектов нет.
- QR: генерация — `react-native-qrcode-svg`, сканирование — `react-native-camera-kit`. Диплинк-приём сделан вручную через `Linking.addEventListener('url', ...)`, а не через `linking`-конфиг React Navigation — из-за условного корневого навигатора (Splash/Auth/Main) полноценная интеграция линкинга непропорционально сложнее для той же цели.
- Схема `relocantapp://` зарегистрирована в `Info.plist` (`CFBundleURLTypes`) и `AndroidManifest.xml` (intent-filter на `MainActivity`); добавлены `NSCameraUsageDescription`/`NSPhotoLibraryUsageDescription` (iOS) и `CAMERA` permission (Android) для QR-сканера и пикера фото.

**Сознательно не сделано в этом проходе** (см. коммиты): фото/голосовые сообщения в чате, видеозвонки (Agora — отдельная крупная интеграция), пуши на новое сообщение/заявку в друзья (раздел 10 ещё не реализован), свайп-жест «удалить/заблокировать» в списке чатов (кнопки вместо жеста).

### Жалобы и авто-скрытие, валидация возраста (разделы 7.3, 9 ТЗ)

- **Жалобы** — клиент пишет напрямую в `/reports/{reporterId}_{targetId}_{reason}` (детерминированный id: одна жалоба на пару "автор+цель+причина", повторная жалоба той же причины обновляет тот же документ через `merge`). Правила Firestore разрешают `create` только от своего имени, с `status:'pending'` и причиной из фиксированного списка; `read` запрещён клиенту полностью (жалобы — не публичные данные); `update` разрешён только автору и только для `createdAt`/`comment`/`contentSnapshot`.
- **Авто-скрытие** — Cloud Function `onReportWritten` (триггер на `/reports/{reportId}`) на каждую запись пересчитывает число уникальных авторов жалоб с тем же `targetId`+`reason` и выставляет `autoHidden:true` (+`autoHiddenAt`), когда порог достигнут. Пороги (`functions/src/reports/autoHideThresholds.ts`): критичные причины (`underage`, `inappropriate_content`) — **1** жалоба, остальные — **5**. `autoHidden`/`autoHiddenAt` — Cloud-Function-only поля (тот же паттерн `protectedUserFields()`, что и у `verified`/`premium`); клиент не может их снять — предполагается ручная модерация через отдельную веб-панель (см. ТЗ 7.3: "этот веб-инструмент — отдельная задача разработки", в мобильный скоуп не входит).
- Скрытый пользователь уже исключался из ленты свайпов (`isEligibleCandidate`); теперь дополнительно невидим для поиска по `@username` в разделе "Добавить друга" — чтобы не выдавать сам факт скрытия, ответ для скрытого профиля тот же, что и для несуществующего юзернейма.
- Точки жалобы в UI: кнопка "⚑" на верхней свайп-карточке, ссылка "Пожаловаться" в шапке чата, long-press на чужом сообщении (передаёт текст сообщения как `contentSnapshot`).
- **Валидация возраста 18+** (раздел 9) — числовое поле `age` в профиле теперь проверяется в двух местах: в `ProfileScreen` перед сохранением (блокирует сабмит с понятной ошибкой) и в `firestore.rules` (`validAge()` на `create`/`update` документа `/users/{uid}`) как defense-in-depth на случай обхода клиента. Обязательный чекбокс "мне есть 18" при входе — отдельная сущность (подтверждение факта, не дата рождения) и не менялся.

### Аудит по ТЗ и рефакторинг (см. `docs/STATUS.md` для полной сверки по разделам)

Полный проход по всем 14 разделам ТЗ против кода; найденные и исправленные баги/отклонения:

- **Баг: нельзя было очистить био.** `submitProfileTextInputSchema` требовал `value.min(1)`, хотя доменное правило (`FIELD_LENGTH_LIMITS.bio.min = 0`) разрешает пустую строку — `ProfileScreen` при попытке очистить био получал `invalid-argument` от Cloud Function. Убрали нижнюю границу из zod-схемы, доменная проверка длины по полю осталась единственным источником правды по границам.
- **Гонка в `submitProfilePhoto`.** Проверка "не больше 6 фото" и запись в `avatarUrls` не были атомарны — два параллельных запроса могли оба пройти проверку и превысить лимит. Проверка лимита перенесена в `runTransaction` с повторным чтением перед записью; если гонка всё же обнаружена на этом этапе, уже опубликованный файл удаляется, чтобы не оставлять "осиротевшую" фотографию в Storage.
- **Дублирование `buildPairId`/`buildChatId`.** Одна и та же формула (`[a,b].sort().join('_')`) была продублирована в `entities/chat/model/types.ts` и локально в `entities/friend/api/friendApi.ts`. Вынесено в `shared/lib/pairId.ts`, `buildChatId` теперь тонкая обёртка над ним. (Серверная копия в `functions/src/shared/pairId.ts` остаётся отдельной — другой npm-пакет, другой рантайм.)
- **Неверный комментарий в `userApi.ts`**, утверждавший, что защищённые поля (`verified`/`premium`/...) инициализирует некий auth-триггер Cloud Function — такого триггера не существует (эти поля просто отсутствуют в документе, пока их не выставит соответствующая функция). Комментарий исправлен.
- **`unblockUser` был мёртвым кодом.** Функция существовала в `entities/chat`, но ни один экран её не вызывал — разблокировать пользователя после блокировки было невозможно через UI. Добавлен список заблокированных пользователей с кнопкой "Разблокировать" в `PrivacySettingsScreen`.
- **`FriendsScreen` рендерил растущие списки (заявки в друзья, список друзей) через `ScrollView` + `.map()`** — нарушение правила 14.1 ("FlatList/FlashList, не `.map()`+`ScrollView`") и потенциальная проблема производительности на больших списках. Переведено на `SectionList` с двумя секциями.
- **Полное отсутствие структурированного логирования в Cloud Functions** (правило 14.2) — добавлены `functions.logger` вызовы в ключевых точках: отклонение модерации (фото/текст/сообщение), создание мэтча, блокировка пользователя, авто-скрытие по жалобам.
- **`android/build.gradle`: `minSdkVersion = 24`**, при требовании ТЗ Android 8.0/API 26+. Исправлено на 26.
- Схемы валидации `removeProfilePhoto`/`reorderProfilePhotos` были объявлены инлайн в файлах функций вместо общего `moderation/schema.ts` — вынесены туда же, где лежат остальные схемы модуля, для единообразия.

**Найдено, но не исправлено в этом проходе** (см. `docs/STATUS.md`):
- Самостоятельное удаление аккаунта (§12) — единственный явно MVP-обязательный пробел без внешних зависимостей.
- App Check установлен как зависимость, но нигде не инициализирован и не включён на callable-функциях — требует регистрации в Firebase Console и тестирования на устройстве, недоступного в этой среде.
- Онбординг (3.3) в ТЗ описан как последовательность skip-able экранов; реализован как единая форма в профиле — функционально эквивалентно, но другой UX-поток. По запросу оставлено как есть.

### Фото/голосовые сообщения и непрочитанные (разделы 6.1, 6.2, 6.3 ТЗ)

- **Фото и голосовые сообщения** — новая Cloud Function `sendChatMedia` (параллельно `sendMessage`, тот же коннекшн-чек через общий `getConnectionForPair`): клиент грузит файл в приватный staging `chats/{chatId}/pending/{uid}/...`, функция для фото прогоняет Google Vision SafeSearch (как и профильные фото), затем публикует файл и пишет сообщение с `type: 'image'|'voice'`. Голосовые — без автомодерации: осмысленного аудио-пайплайна нет без новой внешней зависимости (speech-to-text + текстовая модерация, либо отдельный сервис) — задокументированный пробел, см. `docs/STATUS.md`.
- Опубликованное медиа чата устроено так же, как фото профиля — публичный неугадываемый URL, а не Storage Rules, ограниченные участниками пары. Более строгий вариант потребовал бы cross-service правил Storage→Firestore или подписанных URL с истечением; не реализовано, т.к. не может быть проверено end-to-end без реального деплоя/устройства в этой среде.
- Запись/воспроизведение — `react-native-audio-recorder-player@3.6.14` (сознательно взята устаревшая до-Nitro версия: у v4+ появляется зависимость от `react-native-nitro-modules`, которую нельзя ни собрать, ни проверить в этой песочнице). Разрешения: `NSMicrophoneUsageDescription` (iOS), `RECORD_AUDIO` (Android, запрашивается в рантайме).
- **Индикатор непрочитанных** — `/chats/{chatId}.readBy: {[uid]: Timestamp}`, обновляется тем же Cloud Function, что и отправка (`sendMessage`/`sendChatMedia` стемпают `readBy` отправителя), и отдельным callable `markChatRead` (вызывается клиентом при открытии чата и на каждое новое сообщение, пока экран открыт) — `/chats` остаётся полностью Cloud-Function-only по правам, поэтому чтение отмечается через callable, а не прямой записью клиента в один вложенный ключ. Чистая функция `isChatUnread` в `entities/chat` сравнивает `lastMessageAt` с собственным `readBy`.
- Удалено мёртвое поле `Message.readAt` (было объявлено, нигде не читалось и не писалось) в пользу реальной реализации через `Chat.readBy`.

**Сознательно не сделано в этом проходе**: удаление аккаунта (§12, единственный явно MVP-обязательный пробел без внешних зависимостей — см. `docs/STATUS.md`), App Check, видеозвонки и верификация/монетизация (внешние интеграции), пуш-уведомления (не выбраны для этого прохода, хотя технически не требуют кода с внешними кредами).

### Приватность выдачи и медиа, серверная лента (разделы 4.2, 4.2.1, 6.1, 12 ТЗ)

Проход по слабым местам, найденным в ревью проекта.

- **Лента свайпов переехала на сервер** — callable `fetchSwipeCandidates` (`functions/src/feed`). Раньше клиент сам запрашивал `/users` и фильтровал выдачу (блокировки, авто-скрытие по жалобам, взаимный фильтр по полу) уже после загрузки документов на устройство, а правило `/users` разрешало чтение любому авторизованному пользователю — то есть скрытые и заблокированные анкеты всё равно приезжали на клиент, а прямой запрос через Firestore SDK обходил фильтры ленты целиком. Теперь фильтрация выполняется до отдачи, наружу уходит только белый список полей (`PublicProfile`: без `blockedUserIds`, счётчиков лимитов, `autoHidden`, `sortKey`), а страна/язык для фильтра берутся из профиля вызывающего, а не из запроса.
- **`/users` больше не читается сплошь**: правило разрешает чтение своего документа, документов тех, с кем уже есть мэтч/дружба/чат, и тех, кого вы заблокировали (для экрана «Заблокированные»). Поиск по `@username` для незнакомых людей — через callable `lookupUserByUsername`, который отдаёт `null` для авто-скрытых и для заблокированных пар, не раскрывая, какой именно случай.
- **Устранён перекос случайной выдачи (4.2.1).** Скан `sortKey` шёл только вперёд от случайной точки и не заворачивался в начало диапазона — анкеты с высоким `sortKey` системно показывались реже. Теперь проход круговой: доходит до конца диапазона, продолжает с нуля и останавливается непосредственно перед точкой старта; когда круг пройден, сервер возвращает `nextCursor: null`, и клиент перестаёт запрашивать (раньше он бесконечно начинал новый проход со случайной точки). Покрыто тестами (`scanForCandidates.test.ts`), включая проверку «любая анкета достижима из любой стартовой точки».
- **Медиа чата стало приватным.** Фото и голосовые больше не публикуются: `sendChatMedia` хранит в сообщении путь в Storage, а не URL, правило `chats/{chatId}/media/{fileName}` пускает на чтение только два uid, зашитых в `chatId`, и клиент получает download-URL сам (`resolveChatMediaUrl`). Фото профиля остаются публичными — они должны грузиться в чужих лентах.
- **Баг правил Firestore: чтение несуществующего документа пары.** `/matches/{id}` и `/friends/{id}` разрешали чтение условием на `resource.data`, а Firestore отклоняет такое чтение, когда документа нет — то есть штатные проверки «есть ли уже мэтч/заявка» (перед отправкой заявки в друзья и при показе кнопки «Добавить в друзья») падали с `permission-denied`. Для `get` случай отсутствующего документа выделен явно и ограничен двумя uid из id пары.
- **Баг авто-стопа голосового сообщения.** При достижении лимита длительности обработчик читал `elapsedSeconds` из устаревшего замыкания; в граничном случае запись отбрасывалась как «короче секунды». Счётчик продублирован в `ref`, который и читает путь остановки.
- **Модерация текста переосмыслена (7.2).** В личных сообщениях фильтр выключен: между двумя людьми, которые уже согласились на контакт, словарь мата блокирует обычный разговор взрослых и при этом не ловит реальные проблемы ЛС (харассмент, скам, несовершеннолетние) — их закрывают жалобы с авто-скрытием (7.3) и блокировка (6.2). Это осознанное отклонение от формулировки ТЗ, решение продукта. Для публичных полей (имя, «о себе») фильтр остался и стал многоязычным: `obscenity` для английского (ловит обфускацию вида `f*ck`, `sh1t`) + `bad-words-next` со словарями en/ru/ru_lat/ua/es/fr/de/pl — они матчат основы, поэтому словоформы («блядью», «хуёвый») и подстановки символов («н@хуй») тоже ловятся. Пробелы, найденные на реальных примерах (в основном русский латиницей), вынесены в `extraProfanity.ts` — одно место, куда дописывать слово, если что-то проскочило. Это словарь, а не классификатор; апгрейд — хостовый API модерации, как и предполагало ТЗ. Фото в чате по-прежнему проходят SafeSearch.
- **Тесты на хуки с побочными эффектами** (раздел 14.1 — раньше тестами была покрыта только чистая логика): `useSwipeFeed` (пагинация, исчерпание пула, лимит свайпов, отсутствие повторной выдачи свайпнутых), `useVoicePlayback` и `useChatVoiceRecorder` (остановка записи/воспроизведения при размонтировании, guard от двойного тапа, отбрасывание слишком коротких записей). Минимальный `renderHook` на `react-test-renderer` — в `shared/lib/testing`.

### Удаление аккаунта (раздел 12 ТЗ)

Обязательное требование App Store (5.1.1v) и Google Play, последний MVP-пункт ТЗ, не требовавший внешних интеграций.

- **Экран `pages/delete-account`**, вход — с вкладки «Профиль», рядом с «Выйти» (Apple требует, чтобы удаление находилось не сложнее, чем регистрация). Экран перечисляет, что именно будет удалено, требует явного подтверждения чекбоксом, и только после этого показывает финальный диалог с деструктивной кнопкой.
- **Callable `deleteAccount`** (`functions/src/account`) выполняет каскад правами админа: `/users`, `/swipes` в обе стороны (`swiperId` и `targetId`), `/matches`, `/friends`, резервация в `/usernames` (юзернейм освобождается), фото профиля и неотправленные staging-файлы в Storage (`users/{uid}/`, `chats/{chatId}/pending/{uid}/`), и последним — сам Auth-пользователь.
- **Порядок важен**: Auth-пользователь удаляется последним, поэтому сбой в середине каскада оставляет аккаунт, под которым можно войти и повторить, а не осиротевшие данные без доступа. Удаление идёт через Cloud Function, а не клиентский `user.delete()`, который падает с `auth/requires-recent-login` у всех, кто входил давно, и не трогает Firestore/Storage.
- **Переписки сохраняются** — чат принадлежит обеим сторонам, поэтому второй участник не теряет историю, включая сообщения и медиа ушедшего. Чат помечается `deletedParticipantIds`, и клиент по этой метке показывает собеседника как «Удалённый пользователь» и переводит чат в read-only: композер заменяется пояснением, действия «пожаловаться»/«заблокировать» скрываются (адресата больше не существует). Сервер и так отказал бы в отправке — `/matches` и `/friends` удалены, `getConnectionForPair` вернёт `not_connected`. Опубликованное медиа чата остаётся на месте, иначе в сохранённой переписке ломались бы фото и голосовые; удаляется только staging ушедшего пользователя — то, что он так и не отправил.
- **Жалобы сохраняются в обе стороны**: и на пользователя (иначе удаление аккаунта стирало бы претензии к нему — очевидный обход модерации), и поданные им (это свидетельства по чужим делам). Упоминания его uid в чужих `blockedUserIds` тоже остаются — безвредно, uid в Firebase не переиспользуется, а чистка потребовала бы скана всей коллекции.
- Хук `useDeleteAccount` покрыт тестами: удаление → сброс локальной сессии, сохранение сессии при ошибке (чтобы можно было повторить), guard от двойного нажатия (через `ref` — state-guard не держит два тапа в одном тике, тот же класс бага, что чинили в голосовом рекордере).

### Push-уведомления (раздел 10 ТЗ)

FCM уже был в стеке, но нигде не инициализирован. Внешних кредов код не требует: `admin.messaging()` работает с правами сервиса, APNs-ключ нужен только для реальной доставки на iOS и загружается в Firebase Console.

- **Триггеры Firestore, а не отправка из callable-функций** (правило 14.2 «одна функция — одна ответственность»): `onMatchCreated` (новый мэтч — обоим), `onMessageCreated` (текст/фото/голосовое — второму участнику), `onFriendshipWritten` (новая заявка в друзья и её принятие). Упавший пуш не может уронить сам мэтч или отправку сообщения.
- **Presence-правило из ТЗ**: пуш о сообщении не отправляется, если получатель прямо сейчас держит этот чат открытым. Флаг снимается не только при уходе с экрана, но и когда приложение уходит в фон — иначе чат, оставленный открытым под заблокированным экраном, глушил бы все уведомления от этого собеседника.
- **Язык уведомления — язык получателя** (§11), не отправителя и не сервера: клиент сохраняет свой язык интерфейса, сервер по нему выбирает шаблон, fallback — английский. Превью текста обрезается до 120 символов; для фото и голосовых показывается описание типа, а не путь в Storage.
- **Тап по уведомлению открывает то, о чём оно**: чат (для сообщения и мэтча) или вкладку «Друзья» (для заявки). Для холодного старта используется `navigationRef` с ожиданием готовности контейнера — на этот момент `useNavigation` ещё недоступен.
- **Жизненный цикл токенов**: регистрация после входа, сохранение при ротации, снятие токена этого устройства при выходе из аккаунта, и чистка на сервере тех токенов, которые FCM отметил как мёртвые (иначе каждое уведомление вечно тратило бы неудачную отправку на удалённое приложение).
- **Push-состояние живёт в `/users/{uid}/private/push`**, а не в профиле: основной документ читают все, с кем вы связаны, а `activeChatId` содержит uid текущего собеседника — на публичном документе он рассказывал бы друзьям и мэтчам, с кем вы переписываетесь прямо сейчас. Попутно `deleteAccount` переведён на `recursiveDelete`, иначе эта подколлекция пережила бы удаление аккаунта.
- Не реализовано: «кто лайкнул профиль» (премиум-фича, §8 не построен) и входящий видеозвонок (§6.4, Agora).

### Офлайн-кэш и App Check (раздел 12, 14.2 ТЗ)

- **Офлайн-персистентность Firestore включена явно** (`app/firebase/init.ts`): нативно она и так работает, но кэш по умолчанию ограничен по размеру и подчищается сборщиком — на активном устройстве это молча вытесняет старую историю чатов. Теперь `persistence: true` и неограниченный размер кэша заданы в коде, а не унаследованы.
- **App Check подключён на клиенте**: debug-провайдеры в dev-сборках, Play Integrity (Android) и App Attest с откатом на DeviceCheck (iOS) — в релизных. Все 12 callable-функций получают опции через общий `callableOptions()`, так что новую функцию нельзя случайно оставить без защиты.
- **Принуждение — переключатель деплоя, а не константа**: `ENFORCE_APP_CHECK` в `functions/.env` (шаблон — `.env.example`), по умолчанию `false`. Включённый App Check до регистрации приложения в Firebase Console отрезает и настоящее приложение тоже, поэтому порядок такой: зарегистрировать → добавить debug-токен → поставить `true` → задеплоить.

### Свайп по чату (раздел 6.2 ТЗ)

Последнее расхождение с ТЗ в реализованной части: «свайп по чату — удалить/заблокировать» было сделано кнопками.

- **`shared/ui/SwipeableRow`** — на `Animated` + `PanResponder`, теми же примитивами, что и колода свайпов, без новой gesture-библиотеки ради одного экрана. Жест перехватывается только если он явно горизонтальный, иначе список перестал бы скроллиться; строка не останавливается на полпути — либо открыта, либо закрыта. Логика вынесена в чистые функции (`swipeRowGesture.ts`) и покрыта тестами, сам компонент — тонкая обёртка над ними.
- **«Удалить» скрывает чат только у себя** (`hideChat`, стемп `hiddenAt.{uid}`), а не стирает у собеседника: переписка принадлежит обеим сторонам, как и при удалении аккаунта. Стемп, а не флаг, — потому что сообщение новее стемпа возвращает чат в список, как и ожидается от мессенджера.
- **«Заблокировать»** переиспользует существующий `blockUser`; у собеседника, удалившего аккаунт, это действие не показывается — блокировать больше некого. Оба действия спрашивают подтверждение.

### Что нужно сделать руками (вне кода)

Пошаговая инструкция — в [`docs/SETUP.md`](docs/SETUP.md): аккаунты, где что
скопировать и куда вставить. Кратко:

1. **Firebase config-файлы**: положить `android/app/google-services.json` и `ios/ReloDating/GoogleService-Info.plist` из своего Firebase-проекта. Без них приложение не стартует.
2. **Push на iOS**: загрузить APNs-ключ в Firebase Console (Cloud Messaging) и включить capability «Push Notifications» в Xcode для таргета. На Android ничего не требуется — разрешение уже в манифесте.
3. **App Check**: зарегистрировать приложения (Play Integrity / App Attest), добавить debug-токен из лога dev-сборки, затем `ENFORCE_APP_CHECK=true` и редеплой. Отдельно в консоли можно включить принуждение для Firestore и Storage.
4. **Google Cloud Vision API**: включить API и биллинг в проекте — на нём держится модерация фото (7.2).
5. **Деплой**: `firebase deploy --only firestore:rules,firestore:indexes,storage,functions` — правила, индексы и функции в этом репозитории уже обновлены под всё вышеописанное.
