# Техническое задание
## Мобильное приложение знакомств для релокантов

**Платформы:** iOS, Android
**Стек:** React Native (кроссплатформа), TypeScript
**Бэкенд:** Firebase (Authentication, Firestore, Cloud Storage, Cloud Functions, Cloud Messaging)
**Видеозвонки:** Agora SDK (отдельная интеграция, не входит в Firebase)

---

## 1. Концепция

Приложение для знакомств между людьми, переехавшими жить в другую страну (релокантами), и/или знакомств с местными жителями. Ключевая идея — фильтрация по стране текущего проживания и/или родному языку, что отличает продукт от универсальных дейтинг-приложений.

---

## 2. Общая структура приложения

Нижняя навигация (tab bar), 4 вкладки:

1. **Профиль** — просмотр/редактирование своей анкеты, настройки
2. **Свайпы** — лента анкет (карточки, свайп влево/вправо, как в Tinder)
3. **Друзья** — список друзей (не то же самое, что мэтчи)
4. **Сообщения** — список чатов, личная переписка

---

## 3. Регистрация и авторизация

### 3.1 Способы входа
- Sign in with Apple
- Google Sign-In
- Email + пароль
- Номер телефона (SMS-код через Firebase Phone Auth)

**Объединение аккаунтов:** если пользователь входит новым способом (например, Google) с тем же email, что уже зарегистрирован через другой способ (например, email/пароль) — Firebase Auth даёт ошибку `auth/account-exists-with-different-credential`. В этом случае показать экран "Похоже, у вас уже есть аккаунт — войдите способом, использованным ранее, чтобы привязать новый метод входа", и после успешного входа старым способом — привязать новый провайдер через `linkWithCredential`. Не создавать два разных `/users/{uid}` документа для одного и того же человека.

### 3.2 Поля анкеты при регистрации

**Обязательные:**
| Поле | Тип | Валидация |
|---|---|---|
| Имя | текст | 2–30 символов |
| Текущая страна | select из списка стран (ISO 3166) | обязательное поле |
| Родной язык | select из списка языков (ISO 639-1) | обязательное поле |

**Опциональные (можно заполнить позже, в профиле):**
| Поле | Тип | Примечание |
|---|---|---|
| Возраст | число | самодекларация, без проверки документа; минимум 18 (см. п.9) |
| Увлечения | multi-select тегов | список см. Приложение A, лимит — до 10 тегов на профиль |
| Фото | до 6 изображений | первое фото — главное, отображается в свайпах. **Минимум 1 фото обязателен, чтобы анкета появлялась в ленте свайпов** (без фото — доступ к своему профилю есть, но в чужие ленты пользователь не попадает) |
| О себе | текст | до 500 символов |
| Юзернейм | текст, уникальный | для добавления в друзья по поиску (см. п.6). Формат: 3–20 символов, латиница/цифры/нижнее подчёркивание, проверка уникальности регистронезависимая. Можно менять в любое время в настройках — деплинки-приглашения используют `uid`, а не юзернейм, поэтому смена не ломает уже отправленные ссылки/QR. |
| Пол | select: мужской/женский/другое | опционально, используется как фильтр в свайпах |
| Кого ищет | select: мужчин/женщин/всех | опционально, используется как фильтр в свайпах |
| Здесь с | месяц + год (picker) | опционально; используется для бейджа "стажа" (см. 3.4) |

### 3.4 Бейдж "стажа в стране"
Вычисляется на клиенте/Cloud Function из поля "Здесь с" (разница между текущей датой и указанной):
| Стаж | Бейдж на карточке |
|---|---|
| < 1 месяца | "Новенький(ая) в стране" |
| 1–6 месяцев | без бейджа |
| ≥ 6 месяцев | "Старожил" |

Если поле не заполнено — бейдж не показывается. Бейдж — часть иконки на карточке в ленте свайпов (см. 4.1), не отдельный экран.

### 3.3 Онбординг — экраны (для юниора, порядок обязателен)
1. Splash screen
2. Выбор способа входа
3. (если email/phone) — подтверждение (код из письма/SMS)
4. Ввод имени
5. Выбор текущей страны
6. Выбор родного языка
7. (опционально, с кнопкой «Пропустить») — возраст → пол → кого ищет → «здесь с» → увлечения → фото → «о себе» → юзернейм
8. Переход на вкладку «Свайпы»

## 4. Свайпы (лента знакомств)

### 4.1 Механика
- Карточка анкеты: фото (свайп по фото листает остальные фото этого пользователя), имя, возраст (если указан), страна, теги увлечений, бейдж стажа (см. 3.4), процент совпадения (см. 4.5).
- Свайп вправо — лайк, свайп влево — дизлайк, кнопка "назад" (отмена последнего свайпа) — **только для премиум**.
- При взаимном лайке — создаётся мэтч, показывается экран "It's a match" с кнопкой "Написать сообщение".

### 4.2 Фильтры ленты
Пользователь выбирает в настройках фильтра один из режимов:
1. Только текущая страна
2. Только родной язык
3. Страна + родной язык (пересечение)

Дополнительно к любому из режимов можно сузить:
- Возрастной диапазон (мин–макс)
- Теги увлечений (показывать только тех, у кого совпадает хотя бы 1 тег)
- Пол (если заполнен у пользователя)

Лента по умолчанию учитывает поле "Кого ищет" **взаимно, в обе стороны**: пользователь A видит в ленте только тех B, чей пол соответствует `A.lookingFor`, **и одновременно** пол `A` соответствует `B.lookingFor`. Если у одной из сторон "Кого ищет" не заполнено — фильтр по полу с этой стороны не применяется (не блокирует показ). Другими словами: пара исключается из обеих лент, если хотя бы у одного из двоих указано конкретное предпочтение, которому другой не соответствует.

Пользователи без заполненного опционального поля (возраст/язык уже обязателен, значит только возраст может отсутствовать) — исключаются из фильтров, где это поле требуется.

### 4.2.1 Базовая сортировка ленты
Внутри отфильтрованного пула анкет (после применения фильтров п.4.2) порядок — **случайный** (shuffle при каждой загрузке порции ленты), без сортировки по compatibility score или активности — это сознательный выбор в духе классического Tinder, чтобы не создавать эффект "богатые становятся богаче" для анкет с высоким score.

Поверх случайного порядка применяются точечные корректировки:
- Активный **буст** (см. 4.3) — анкета временно поднимается в начало пула на время действия буста.
- **Верифицированные** пользователи (см. 7.1) — при прочих равных показываются чаще, чем неверифицированные (лёгкий вес в выборке, не жёсткая сортировка сверху вниз, чтобы не превращать ленту в статичный список "сначала все верифицированные").

### 4.3 Лимиты (freemium)
- Бесплатный тариф: **20 свайпов в сутки**, счётчик обнуляется в 00:00 по таймзоне устройства.
- Премиум: безлимитные свайпы + отмена последнего свайпа + фильтр "кто лайкнул меня" + буст анкеты (показ выше в чужих лентах на 30 минут, 3 буста в месяц).

### 4.4 Модель данных (Firestore)
```
/users/{uid}
/swipes/{swipeId}          // swiperId, targetId, action: 'like'|'dislike', createdAt
/matches/{matchId}         // userIds: [uidA, uidB], createdAt, lastMessageAt
```
Мэтч создаётся Cloud Function-триггером на запись в `/swipes`: если существует встречный лайк `targetId→swiperId`, создать документ в `/matches` и отправить push обоим.

### 4.5 Compatibility score ("% совпадения")
Показывается на карточке в ленте (правый верхний угол, например "78% match"). Считается на клиенте при построении ленты, без отдельного запроса.

Формула (простая взвешенная сумма, MVP):
```
score = countryMatch(0|40) + languageMatch(0|30) + interestsScore(0..30)

countryMatch    = 40, если currentCountry совпадает, иначе 0
languageMatch   = 30, если nativeLanguage совпадает, иначе 0
interestsScore  = min(sharedInterestsCount, 3) / 3 * 30   // максимум при 3+ общих тегах
```
Итог округляется до целого процента. Если у одного из пользователей не заполнены увлечения — `interestsScore = 0`, это не ошибка.

> Формула — стартовая версия для MVP, веса можно будет тюнинговать после сбора данных о конверсии в мэтч.

## 5. Мэтчи vs Друзья — разграничение

Это **две разные сущности**, друзья не равны мэтчам:

- **Мэтч** — результат взаимного свайпа. Даёт доступ к чату. Хранится в `/matches`.
- **Друг** — запись в отдельном списке `/friends`, добавляется:
  - автоматически, если пользователь нажал "Добавить в друзья" из чата с мэтчем (без подтверждения — обе стороны уже согласились на контакт через мэтч);
  - вручную, без свайпа — через **QR-код / диплинк-приглашение** или через **поиск по юзернейму**, в этом случае — **с подтверждением принимающей стороны** (см. 5.2).

Добавление в друзья по умолчанию открывает чат без мэтча. Пользователь может отключить это в настройках приватности (см. ниже) — тогда чат с друзьями без мэтча будет недоступен, только просмотр профиля.

**Настройка приватности** (экран "Настройки → Приватность"):
- Тумблер "Разрешить сообщения от друзей без мэтча" — по умолчанию **включён**. При выключении: существующие чаты с друзьями-без-мэтча переходят в read-only (новые сообщения отправлять нельзя, история сохраняется).

### 5.1 Модель данных
```
/friends/{friendshipId}
  userIds: [uidA, uidB]
  requestedBy: uid              // кто инициировал
  addedVia: 'match' | 'qr' | 'username_search'
  status: 'pending' | 'accepted' | 'declined'
  createdAt, respondedAt?
```
Для `addedVia: 'match'` статус сразу `'accepted'`. Для `'qr'` и `'username_search'` — создаётся со статусом `'pending'`, чат становится доступен только после перехода в `'accepted'`.

### 5.2 Поиск и приглашение
- У каждого пользователя есть уникальный `@username`.
- Экран "Добавить друга": поле поиска по `@username` + кнопка "Показать мой QR-код" + кнопка "Сканировать QR".
- QR-код кодирует диплинк вида `relocantapp://addfriend/{uid}`.
- После отправки заявки (по юзернейму или QR) — принимающая сторона получает push-уведомление и видит заявку в списке "Заявки в друзья" (отдельный подраздел на вкладке "Друзья") с кнопками "Принять" / "Отклонить".
- Только после "Принять" запись переходит в `status: 'accepted'`, и у отправителя в списке друзей появляется новый контакт с возможностью открыть чат (если у него включена настройка выше).

## 6. Личные сообщения

### 6.1 Типы контента в чате
- Текст
- Фото (из галереи или камеры)
- Голосовые сообщения (запись в приложении, воспроизведение с прогресс-баром)
- Видеозвонки (кнопка в шапке чата, звонок через Agora RTC)

### 6.2 Список чатов (вкладка "Сообщения")
- Сортировка по последнему сообщению.
- Индикатор непрочитанных.
- Свайп по чату — удалить/заблокировать пользователя.
- **`chatId` — детерминированный** (например, отсортированная конкатенация двух `uid` через `_`), чтобы между парой пользователей всегда существовал ровно один чат независимо от того, как возникла связь (мэтч и/или дружба) — не создавать второй чат при последующем мэтче между уже переписывающимися друзьями.
- **Блокировка пользователя:** удаляет записи в `/matches` и `/friends` между парой (если есть), скрывает пользователя из будущих выдач ленты свайпов в обе стороны, переводит существующий чат в read-only для заблокированного (сообщения от него не доставляются). История чата не удаляется у блокирующего. Заблокированный не получает явного уведомления о блокировке — просто перестаёт видеть новую активность собеседника.
- **Экран "Настройки → Заблокированные пользователи":** список всех, кого пользователь заблокировал (по `blockedUserIds`), с кнопкой "Разблокировать" у каждого. Разблокировка убирает `uid` из `blockedUserIds` и возвращает пользователя в пул ленты свайпов (мэтч/дружба и история свайпов при этом не восстанавливаются — их придётся создавать заново через новый свайп/заявку).

### 6.3 Модель данных
```
/chats/{chatId}                       // participantIds: [uidA, uidB], lastMessage, lastMessageAt
/chats/{chatId}/messages/{messageId}  // senderId, type: 'text'|'image'|'voice'|'call_log', content/url, createdAt, readAt
```

**Схема `call_log`-сообщения (при `type: 'call_log'`):**
```
callerId, calleeId, durationSeconds, status: 'answered' | 'missed' | 'declined'
```
Отображается в чате как системная строка ("Видеозвонок · 4:32" / "Пропущенный видеозвонок").

### 6.4 Видеозвонки
- Инициация звонка создаёт запись `call_log` в чате.
- Входящий звонок — push-уведомление + full-screen incoming call UI (даже если приложение свёрнуто, через FCM data-сообщение + CallKit/ConnectionService).
- **Лимит для бесплатного тарифа: 15 минут видеозвонков в сутки** (совокупно по всем звонкам, не за один звонок), счётчик обнуляется по серверному времени (см. п.12, анти-абьюз). При достижении лимита — звонок завершается автоматически с предупреждением за 30 секунд.
- **Если хотя бы у одного из двух собеседников активна премиум-подписка — лимит не действует для обоих на этот звонок**, и время этого звонка **не списывается** с суточной квоты бесплатного участника (проверка `premium === true` у любого из участников на старте звонка отключает списание для пары целиком на весь звонок).
- Премиум: звонки без ограничения по длительности.

## 7. Верификация профиля и модерация

### 7.1 Верификация (badge "Verified")
- Перед первым запуском верификации — экран согласия на обработку биометрических данных (сравнение лиц юридически относится к чувствительным персональным данным в GDPR и аналогичных законах) с явным чекбоксом "Согласен(на)", без которого функция недоступна.
- Пользователь снимает селфи прямо в приложении (запрет загрузки из галереи, чтобы исключить чужое фото).
- Cloud Function отправляет селфи и текущее главное фото профиля в сервис сравнения лиц (например, AWS Rekognition CompareFaces или аналог) → при совпадении выше порога — ставится флаг `verified: true`.
- Статус верификации виден в профиле (галочка) и влияет на видимость в ленте (неверифицированные — по умолчанию ниже в выдаче, настраивается фильтром "показывать только верифицированных").

### 7.2 Автоматическая модерация контента
**Область действия:** модерация применяется ко всему пользовательскому контенту без исключений — фото профиля, фото и текст в сообщениях чата, фото и текст события (см. 13.1), поля "имя" и "о себе".

- Все загружаемые фото (профиль, чат, события) проходят через модерацию (например, Google Cloud Vision SafeSearch / AWS Rekognition Moderation) до публикации/отправки — при обнаружении запрещённого контента (нагота, насилие) фото отклоняется, пользователю показывается ошибка.
- **Текст в чате проверяется синхронно, до отправки:** при нажатии "Отправить" сообщение сначала уходит на проверку в Cloud Function (модерируемый список слов + сторонний API, например OpenAI Moderation API), и только после положительного результата попадает в `/chats/{chatId}/messages`. UI показывает индикатор отправки (спиннер на сообщении) на время проверки — ожидаемая задержка порядка 300–800 мс, не блокирует ввод следующего сообщения. При обнаружении нарушения — сообщение не сохраняется и не доставляется, отправителю показывается ошибка "Сообщение не может быть отправлено".
- Текст в других полях (имя, "о себе", название/описание события) — та же проверка синхронно при сохранении/публикации.
- Заблокированный/отклонённый контент не публикуется, пользователь получает уведомление с причиной.

### 7.3 Жалобы и модерация

**Подача жалобы:**
- Кнопка "Пожаловаться" на профиле и на отдельном сообщении в чате.
- Причины (select): спам, оскорбления, фейковый профиль, неприемлемый контент, несовершеннолетний, другое (с полем комментария).
- Один пользователь может подать только одну жалобу на одного и того же адресата с одной и той же причиной (повторная — обновляет `createdAt`, не создаёт дубликат).
- При подаче жалобы на сообщение — в жалобу сохраняется **снимок содержимого на момент жалобы** (текст/URL фото), чтобы последующее удаление/редактирование сообщения не мешало модератору увидеть исходник.

**Авто-скрытие (автоматическое, без участия модератора):**
- Срабатывает по количеству **уникальных** жалобчиков на одного пользователя.
- Причины "несовершеннолетний" и "неприемлемый контент" — авто-скрытие уже с **1 жалобы** (быстрая реакция на критичные случаи).
- Остальные причины (спам, оскорбления, фейковый профиль, другое) — авто-скрытие при **5 уникальных жалобах**.
- Эффект авто-скрытия: пользователь полностью исчезает из чужих лент свайпов, поиска по юзернейму и списков друзей у тех, с кем ещё не связан. Уже существующие чаты остаются доступны (чтобы можно было продолжить разбирательство/обжаловать), сам скрытый пользователь может пользоваться приложением как обычно, кроме появления в чужой выдаче.
- Авто-скрытие снимается только вручную модератором (решение "жалоба необоснованна") — автоматического снятия по таймеру нет.

**Модель данных:**
```
/reports/{reportId}
  reporterId, targetId, reason, comment?,
  contentSnapshot?,      // текст/URL на момент жалобы, если жалоба на сообщение
  status: 'pending' | 'resolved_dismissed' | 'resolved_banned',
  createdAt, resolvedAt?, resolvedBy?

/users/{uid}
  ...
  autoHidden: bool        // выставляется Cloud Function-триггером при достижении порога
  autoHiddenAt?: timestamp
```
Подсчёт уникальных жалобчиков — Cloud Function-триггер на создание документа в `/reports`: считает `distinct(reporterId)` по `targetId` за всё время, сравнивает с порогом для данной причины, при превышении — выставляет `autoHidden: true`.

**Админ-панель для модераторов (отдельный веб-инструмент, вне скоупа мобильного приложения):**
Минимальные требования, чтобы жалобы вообще было кем и чем обрабатывать:
- Очередь `/reports` со статусом `pending`, с сортировкой по срочности (сначала причины "несовершеннолетний"/"неприемлемый контент").
- Карточка жалобы: данные обеих сторон (профиль репортящего и репортуемого), причина, комментарий, `contentSnapshot` при наличии, история предыдущих жалоб на этого же `targetId`.
- Два действия: "Отклонить" (снимает `autoHidden`, статус → `resolved_dismissed`) и "Забанить" (полная блокировка аккаунта — нельзя войти, статус → `resolved_banned`).
- Список забаненных/скрытых аккаунтов с возможностью поиска — чтобы видеть, кто скрыт и почему.

> Этот веб-инструмент — отдельная задача разработки (не мобильное приложение), но без него авто-скрытие технически бессмысленно: жалобы будут копиться в очереди, которую некому разобрать.

- **Firestore Security Rules** — обязательная часть разработки, не отдельная фича: пользователь может писать только в свой `/users/{uid}`, не может напрямую менять `swipesUsedToday`, `verified`, `premium` (эти поля пишутся только из Cloud Functions с правами администратора). Без этого клиент может накрутить лимиты и премиум-статус через прямой вызов Firestore SDK.
- **Cloud Storage Security Rules** — аналогично Firestore: пользователь может загружать файлы только в свою папку (`/users/{uid}/...`), лимит размера файла на уровне правил (например, до 10 МБ на фото/голосовое), запрет чтения чужих приватных файлов напрямую по URL без токена (публичный доступ — только к уже опубликованным фото профиля/событий).
- **Анти-абьюз для суточных лимитов:** сброс `swipesUsedToday` и счётчика минут звонков — не полагаться на таймзону устройства (пользователь может её менять, чтобы обходить лимит). Считать сутки от `swipesResetAt`, выставляемого и проверяемого только на стороне Cloud Function по серверному времени (UTC).

## 14. Стандарты и правила написания кода

### 14.1 Frontend — архитектура (Feature-Sliced Design)

Проект строится по FSD. Слои сверху вниз, импорты **только вниз**, никогда вбок и вверх:

```
app/          — точка входа, провайдеры (navigation, theme, auth), инициализация Firebase
pages/        — экраны (композиция виджетов/фич под конкретный роут: SwipesScreen, ChatScreen)
widgets/      — крупные самостоятельные блоки UI (TabBar, MatchModal, ChatHeader)
features/     — юзер-кейсы с бизнес-логикой (swipe-card, send-message, add-friend, subscribe-premium)
entities/     — бизнес-сущности и работа с ними (user, match, chat, event) — модели, API-запросы, базовые UI-компоненты сущности
shared/       — переиспользуемое без бизнес-смысла: UI-кит (Button, Input), хуки, утилиты, конфиг Firebase
```

**Обязательные правила:**
- Каждый слайс (папка внутри слоя, например `features/swipe-card`) отдаёт наружу только через `index.ts` (public API) — импорт напрямую из внутренних файлов слайса (`features/swipe-card/model/store.ts`) из другого слайса запрещён.
- `entities` не знают про `features`, `features` не знают про `widgets`/`pages`. Нарушение — повод для code review отклонить PR.
- Внутри слайса — сегменты `ui/`, `model/` (состояние, бизнес-логика), `api/` (запросы к Firebase). UI-компонент не должен напрямую дёргать Firestore — только через `api/`.
- Именование: компоненты — `PascalCase`, хуки — `useCamelCase`, файлы стора — `model.ts`/`store.ts`, типы — `types.ts` рядом со слайсом, не в общей свалке.

**Состояние:**
- Локальное UI-состояние — `useState`/`useReducer`.
- Кросс-компонентное состояние (текущий пользователь, лента свайпов, счётчики лимитов) — **Zustand** (проще для новых участников команды, минимум boilerplate). Effector — опционально, если понадобится сложная асинхронная оркестрация (например, пайплайн модерации на клиенте перед отправкой).
- Server state (данные из Firestore) — не дублировать вручную в Zustand: подписка на Firestore через хуки (`onSnapshot`) с локальным кэшем на уровне `entities/*/api`, Zustand — только для производного/UI-состояния поверх этих данных.

**Прочее:**
- TypeScript strict mode обязателен (`strict: true` в tsconfig), `any` — запрещён без явного комментария-обоснования.
- Бизнес-логика (расчёт compatibility score, проверка лимитов) — не в компонентах, а в `model/` соответствующего слайса, покрывается unit-тестами (Jest) отдельно от UI.
- Стили — `StyleSheet.create`, не инлайновые объекты в `render` (пересоздаются на каждый рендер).
- Изображения — `react-native-fast-image` вместо стандартного `Image` (кэширование, важно для ленты свайпов с фото).
- Списки (лента чатов, свайпы) — `FlatList`/`FlashList`, не `.map()` внутри `ScrollView`.
- Ошибки сети/Firebase — единая обёртка (`shared/api/handleFirebaseError`), не `try/catch` с произвольным текстом в каждом месте вызова.

### 14.2 Backend — Cloud Functions (Node.js + TypeScript)

- Структура — по доменам, не один файл `index.ts` на все функции: `functions/src/{swipes,matches,friends,chat,moderation,payments}/`, каждый домен экспортирует свои триггеры/callable-функции, `index.ts` только реэкспортирует.
- **Никогда не доверять данным от клиента.** Каждая `onCall`-функция и HTTP-эндпоинт валидирует входные данные схемой (`zod`) до какой-либо бизнес-логики — некорректный payload отклоняется на входе, а не падает где-то в середине обработки.
- Поля, которые не должен менять клиент напрямую (`swipesUsedToday`, `verified`, `premium`, `autoHidden`) — пишутся **только** из Cloud Functions с правами администратора; в Security Rules явно запрещена запись этих полей из клиентского SDK (см. п.12).
- Критичные операции с состоянием гонки (создание мэтча по встречному свайпу, списание лимита звонка) — через Firestore **транзакции** (`runTransaction`), не через последовательные read+write без блокировки.
- Firestore-триггеры **не идемпотентны по умолчанию** (могут сработать повторно на один и тот же ивент) — каждый триггер должен быть написан так, чтобы повторный вызов с теми же данными не создавал дубликат (проверка существования документа перед созданием, а не просто "создать").
- Секреты (ключи AWS Rekognition, RevenueCat, Agora) — через Firebase Secret Manager/`functions.config()`, не хардкод в коде и не в публичном репозитории.
- Логирование — через `functions.logger`, структурированные логи (объект, не конкатенация строк), не `console.log`.
- Один Cloud Function — одна ответственность: не совмещать в одном триггере создание мэтча и отправку push и обновление статистики — разбивать на последовательные шаги/отдельные функции, чтобы падение одного шага не убивало остальные молча.
- Rate limiting на дорогие/платные операции (запрос к AWS Rekognition при верификации, к модератору контента) — ограничение по `uid` (например, не чаще 1 попытки верификации в 10 минут), иначе легко положить бюджет API повторными запросами.
- App Check включён для мобильного клиента — Cloud Functions принимают вызовы только от настоящего приложения, а не от произвольного HTTP-клиента с украденными Firebase-конфигами.
- Тесты: Jest для бизнес-логики (расчёт лимитов, compatibility score, пороги авто-скрытия), Firebase Emulator Suite — для проверки Security Rules и триггеров перед деплоем, не тестировать правила вручную на проде.
- Линтинг/форматирование — ESLint + Prettier с едиными правилами на фронт и бэк, husky pre-commit хук, чтобы код с ошибками линта не попадал в репозиторий.
